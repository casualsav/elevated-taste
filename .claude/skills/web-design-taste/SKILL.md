# Web Design Taste

Build-time design taste, backed by a distilled corpus of **real exemplars** (transferable principles + normalized tokens). When you build or refine any UI, **consult the corpus first** — don't invent from defaults, and never ship the generic AI template.

## Decision rule — pick a corpus, then a direction

**Corpus** (which reference set — these are never blended):
- **`production`** *(default)* — usability-first SaaS / app / product / editorial UI. Use for real software: dashboards, forms, data, docs, product marketing.
- **`expressive`** — award / spectacle / brand-experience web. Use **only** for marketing, landing, or brand work. Check every spectacle technique against the production-safety ledger before using it.

**Direction** (aesthetic flavor — orthogonal to corpus): `minimalist` · `brutalist` · `soft` · `editorial` · `expressive`. Infer from the brief; default to `minimalist` for product UI. See `directions/_index.md`.

> A minimalist SaaS dashboard = `production` + `minimalist`. A maximalist launch page = `expressive` + `expressive`/`soft`. The axes compose.

## Workflow — do this BEFORE writing any markup or styles

1. **Pick corpus + direction** (rule above), then **read `taste/owner.md`** — the owner's own verdicts from real builds. Inside its scope an owner rule beats any corpus default or engine pick; name the rule when you apply it.
2. **Let the engine pick the mix (DEFAULT path):**
   `node <repo-root>/tooling/build-sheet.mjs --brief "<the build in a sentence>" [--corpus …] [--direction …] [--when …] [--tags …] --out <project-dir>`
   The engine is deterministic: it picks the **layout archetype first** (recency-rotated against your recent builds — `split-hero` is rationed to 1-in-5), then a donor per layer (palette/type/motion/layout/imagery) with donors from the last 6 builds hard-excluded, ≥2 directions spanned, and one bold layer enforced unless the brief asks for quiet. With `--out` it also writes `taste.preset.json` + `taste.tokens.css` + `taste.lock.json` in one step (= steps 2+4 together). Read the exemplar/pattern files it names and follow its **palette-derivation block** — sample the client's brand assets / content imagery / cultural context first and converge in oklch; the donor palette is the structural anchor, not the answer. Then continue at step 3. Overriding the engine's pick is allowed but must be stated (which layer, why) — silent re-picks are how the monoculture comes back.
   **Manual retrieval (inspection / override path) — per LAYER, not per exemplar** — do NOT read `corpus/index.json` whole (~96k tokens; it burns half your context before you write a line). Run the scored retrieval instead:
   `node <repo-root>/tooling/query.mjs --brief "<the build in a sentence>" [--corpus production|expressive|both] [--direction <dir>] [--when <when_to_use,…>] [--tags <tag,…>] [--json]` (in the repo: `npm run query --`).
   It returns a small ranked shortlist — exemplars + patterns with `why`, palette/motion one-liners, and the exact file paths to read. For a whole-corpus skim under budget there is `corpus/index.summary.json` (~84KB); pull a shortlisted slug's full palette/motion/`requires_tokens`/`knobs` entry from `corpus/index.json` only if you need more than the CLI printed. Then pick a **donor exemplar for each layer you need — palette, type, motion, layout/section patterns, imagery** — instead of shortlisting 2-5 exemplars and drawing everything from whichever one "fits best." Reuse one donor across at most 2 layers; past that you're wholesale-cloning it, which is exactly what this corpus's breadth exists to prevent. **Motion is a mandatory layer, not a conditional one** — it is empirically the layer most often silently dropped. Check the candidate donors' `motion` field and `references/motion-key.md` before deciding a build needs none; landing on zero motion is a legitimate call, but it must be a stated decision (see step 4), never an omission.
3. **Read the shortlist** — this is the whole point; do not skip:
   - `corpus/<corpus>/principles.md` — the synthesized rules. For an app job (dashboard, table, form, settings, sign-in, checkout), its **App screens** section wins where it disagrees with the marketing-page rules.
   - the shortlisted `corpus/<corpus>/patterns/*.md` — their reference implementations are framework-neutral HTML/CSS.
   - `tokens/tokens.json` — the house tokens. For a direction, build its preset: `node tokens/build.mjs --preset=<direction>` → `tokens/tokens.css`.
   - `references/motion-key.md` — the corpus-wide motion menu (keyword → frequency → safety → recipe file). Read this every build, not only "if it's motion work."
4. **Lock the mix.** The engine (step 2 with `--out`) already did this. Manual path: `node <repo-root>/tooling/exemplar-preset.mjs --name <build-slug> --out <project-dir> --layout <archetype> --layout-donor <slug> <donor1>:<fields> <donor2>:<fields> ...` — writes `taste.preset.json` + `taste.tokens.css` + `taste.lock.json` into the project. The lock records which donor covers which layer **and the layout archetype**; the Stop-gate reads it on any session that touches ≥2 UI files (its proxy for "a build, not a spot-fix") and blocks completion unless it names **≥2 distinct donors**, covers **motion** (or carries `"motionWaiver": "<reason>"`), and sets a **layout archetype** (or carries `"layoutWaiver": "<reason>"`). Append the pattern slugs you actually used to the lock's `patterns` array once the sections are built. `/compose <brief>` runs this same picking-and-locking method as an explicit build-sheet deliverable, if you want to show the mix before coding — it is not a different, stronger path; this workflow and `/compose` write and read the same `taste.lock.json`.
5. **Reuse tokens** — use `var(--token)` names for all color / space / type / radius / shadow / motion / tracking. **No hard-coded magic numbers.** Pattern-specific values stay themeable as `var(--knob, fallback)`. Two rules the lint now encodes: display-size type takes the tracking ramp (`--tracking-display` at display sizes → `--tracking-ui` at UI sizes — the bigger the type, the tighter); and in **Tailwind projects**, generate the token preset (`node <repo-root>/tokens/build.mjs --tailwind` → `tokens/tailwind.preset.mjs`, wire it via `presets:`) and use token-named utilities (`bg-surface`, `text-muted`) — default-palette classes (`text-purple-500`) are a lint **error**.
6. **Avoid** everything in `references/anti-patterns.md` (the anti-slop gate).
7. **Redesigning?** Follow `references/redesign-audit.md` — audit the existing UI first. **Live pages get a preview:** a direction change (Overhaul/Greenfield mode) to an already-published page is shown for owner sign-off BEFORE the live file is replaced. Default preview format: a single SELF-CONTAINED .html file delivered to the owner (images inlined as data URIs, no relative asset paths, motion/JS inline) so it opens straight in a browser with all motion working; screenshots and hosted preview paths are supplements, not the deliverable. Only Preserve-mode refinements may modify a live page directly.
8. **Delegating the build to a sub-agent?** Fill `references/design-brief-template.md` and hand over the filled brief — workers execute verbatim payloads reliably; they do not read this corpus.
9. **Emit into the project's stack** (React / Vue / Svelte / plain HTML). No framework present? Use the static preview (`npm run preview`) and adapt the neutral `patterns/` reference impls.
10. **Lint the output** — run the mechanical gate on what will actually ship: `node <repo-root>/tooling/design-lint.mjs <ui-files>`, or for HTML that lives inside another language (server-rendered strings, SSR output), render the page and pipe it: `<render cmd> | node <repo-root>/tooling/design-lint.mjs --stdin --name page.html`. The lint also reads CSS-in-JS tagged templates and `.ts`/`.js` files that carry design decisions. Fix every `error`; treat `warn`s as review notes.
11. **Look at it** — at build scale the Stop-gate captures desktop (1440px) + mobile (375px) screenshots of standalone HTML and blocks once, handing you the PNG paths: **Read them** (the Read tool renders images) and judge against `principles.md` + `anti-patterns.md` — generic-template tells, cramped spacing, dead motion, contrast — before declaring done. For framework output the gate can't render, do the equivalent yourself (run the dev server, screenshot, look). A build you never looked at is not done.
12. **State your sources** — name the exemplar(s) and principle(s) you drew from, per layer.

## Corpus map (open as needed — do not inline these)
- **Retrieval (start here):** `node <repo-root>/tooling/query.mjs --brief "…"` — scored shortlist over the index; skim view `corpus/index.summary.json`; full entries `corpus/index.json` (per-slug lookups only — never read it whole). All generated by `npm run index:build`; never edit by hand
- **Owner taste (read every build):** `taste/owner.md` — rules from the owner's verdicts; source notes in `inbox/`
- **Principles:** `corpus/production/principles.md` · `corpus/expressive/principles.md`
- **Patterns** (section reference impls): `corpus/<corpus>/patterns/`
- **Per-exemplar reads:** `corpus/<corpus>/exemplars/` · normalized snapshots `corpus/<corpus>/tokens/`
- **Tokens:** `tokens/tokens.json` → `tokens/tokens.css`; direction presets `tokens/presets/`
- **Directions:** `directions/` (`_index.md` explains how they compose with the corpus)
- **Craft references:** `references/{anti-patterns,motion,motion-key,components,design-systems,redesign-audit}.md`
- **Cross-build variety memory:** `tooling/recent-donors.mjs` — written automatically by `exemplar-preset.mjs --out` (step 4); `ui-prompt-guard.mjs` reads it and folds an overuse nudge into its injected reminder when the same donor keeps winning. Nothing to run by hand.

## Paths
`corpus/` · `taste/` · `tokens/` · `directions/` paths are relative to the **taste repo root**. The craft `references/` live **next to this SKILL.md file** (`.claude/skills/web-design-taste/references/` in the repo). If this skill is installed globally (`~/.claude/skills/web-design-taste/`), the repo root is recorded in **`REPO_PATH.txt`** next to this file — read it and resolve every `corpus/` · `tokens/` · `directions/` path against that absolute path; `references/` still resolve next to this file. (Background: repo `README.md` → "cross-project install".) If installed as a **plugin** (`web-design-taste@suite-index`), the plugin root IS the repo root — resolve `corpus/` · `tokens/` · `directions/` against `${CLAUDE_PLUGIN_ROOT}`; no `REPO_PATH.txt` needed. Curation tooling (`npm run …`, `node tooling/…`, `tokens/build.mjs`) runs only from the source repo, never from an installed copy.
